## Completion notes

- Completed 2026-08-22 by repairing the recovered WIP commit: it did not compile (roster match-arm type error, missing `DeleteRequest` import, undefined `user_ids_for_family`, str-sized loop variables, an unbound batch constant) — and running the repaired suite against live DynamoDB Local exposed four further runtime defects, fixed and documented below. The suite was actually executed against `dynamodb-local` (17/17 green), not merely compiled.
- Schema: sessions at `SESSION#<hash>/SESSION`, retirement records at `RETIRED#<hash>/RETIRED` with GSI1 filed under `USER#<user>` and family-grouped sort keys (`FAM#<fid>#SESSION#<created_at>`, `FAM#<fid>#RETIRED#<retired_at>`); both carry the numeric `ttl` attribute DynamoDB reaps natively. Pre-rotation items read back through the empty-family sentinel exactly like SQL's NULL columns (generation 0, no rotation timestamp), with negative tests for present-but-mistyped attributes.
- Consistency: every security read is `consistent_read(true)` — live-session lookup, retirement-record lookup, successor re-read in classification, uniqueness-guard resolution, roster reads, and the refresh-path status read (`get_user_by_id`).
- Remediation 2026-08-22: post-completion review found that the consistency list above initially overreached — `get_user_by_id`, the refresh path's status gate on `USER#<id>/PROFILE`, had shipped without `consistent_read(true)`, leaving it the module's only eventually-consistent security read despite this file's step 2 and implementation note 5 of the source spec (the `g3-dynamo-session-read-eventual-consistency` tail). Fixed by adding `.consistent_read(true)` to its `get_item()` chain — the same one-line fix as the classification reads. Gates re-run at fix time: fmt clean; clippy `-D warnings` clean; nextest workspace-wide 468 passed / 50 skipped. No new test was added: DynamoDB Local has no replicas, so a black-box suspend-then-read test cannot distinguish consistent from eventual reads and would pass either way.
- The authoritative roster lives on a dedicated item (`pk = USER#<id>`, `sk = USER`) per the source spec, created inside `create_user`'s transaction alongside profile and guard items; `backfill_session_rosters` covers users predating rosters (idempotent, condition-guarded). Roster arms run inside every mutating transaction: store adds the hash + creates the family entry; rotation swaps `sessions`, moves the family's live pointer, and remembers both generations; single revocation clears the hash and empties the live pointer (the empty sentinel, never attribute removal — a live-less entry would fail the roster's own strict parse). DynamoDB constraints shaped the expressions: a nested SET needs its root attribute to exist (hence the seeded empty map), paths may appear in only one clause (rotation computes the new `sessions` set from a consistent roster read and installs it with one SET — safe because TransactWriteItems locks the user item, so same-user mutations serialize or conflict outright), and the `#f` placeholder binds the actual family id.
- Rotation is one `TransactWriteItems`: conditional delete of the live item (the CAS), conditional put of the retirement record, conditional put of the replacement, and the roster arm. Only statement 0's `ConditionalCheckFailed` maps to `false`; any other cancellation (colliding replacement, missing user item) is a store error — regression-tested via a mid-transaction replacement collision that must leave gen0 intact, no orphaned record, and return an error rather than a lost-race `false`. Legacy rows swap without a retirement record, matching tasks 03–05.
- Revocation enumerates the strongly consistent roster, never GSI1. Owner discovery for `revoke_family` scans the base table under strong consistency filtered on `family_id` (a GSI query would need the owner id it is trying to discover, and index reads cannot be made consistent). Each attempt deletes exactly what the roster names in `BATCH_WRITE_MAX_ITEMS = 25` batches under the bounded `drain_unprocessed` retry/backoff, re-reads the roster, and only clears the family's entry when it still names exactly what was deleted — otherwise retrying against fresh state up to `REVOCATION_MAX_ATTEMPTS = 5`, then erroring rather than reporting partial success. Counts are de-duplicated across attempts. Once the live item is deleted, any concurrent rotation loses its own CAS, so confirm-then-clear cannot be overtaken.
- Coverage: `session_contract::assert_full_conformance(&store, "dynamo-session-conformance")` plus adapter-local tests — legacy first-redemption swap and failed CAS, mid-transaction rollback semantics, per-user retired sweep scoping, immediate post-write revocation completeness (the GSI-staleness window regression: owner discovery via consistent base scan and enumeration via roster make index freshness irrelevant), storage↔roster mutual-consistency after each mutation with a phantom-user store refused, and backfill idempotence. Normal-tier unit tests cover roster parsing (missing attrs → empty; wrong types → errors), retired-item serialisation round trips, keys/TTL, and both retry helpers. All Dynamo tests keep `#[tokio::test] #[ignore = "requires DynamoDB Local"]` gating; assertions are byte-for-byte the shared ones.
